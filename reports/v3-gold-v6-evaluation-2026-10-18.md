# fd-sentiment v3 满样本金标评测（gold-v6，2026-10-18）

> 60 条金标、54 条成功打分、6 条失败。prompt v3、model `deepseek-v4.1-flash`、
> `max_tokens=32000`、串行。**这是该服务第一次在满样本上跑出可判定的评测。**
> 此前归档记录里的「v3 命中率 0.591」是本地 22/60 样本的结论（38 条因失败缺失），
> 统计上不成立；本报告取代它。

## 一、为什么要重跑

生产库 `/data/fd_sentiment.db` 里 `gold_set` 0 条、`eval_runs` 0 条——三代 prompt 的全部分数与评测**从没进过生产库**，只存在于各人本地。换机器即失忆，线上没有任何"准不准"的证据。

本次用 `scripts/build_gold_set.py` 同一批 12 家公司、轮转采样重建 `gold-v6`（60 条：bullish 24 / neutral 24 / bearish 12），标注仍走显式人工规则表（非模型输出）。正文以 sha256 + 长度登记在 `gold/gold-v6.json`，可回源核对；`as_of` 跨 2004-03-11 → 2026-09-21，顺带覆盖 point-in-time。

## 二、三种口径的结果（必须并列看，单独看任一个都会误判）

| 口径 | 结果 | 说明 |
|---|---|---|

| **±1 档内** | **53/54 = 98.1%** | 高度集中在相邻档 |

## 三、偏离结构：不是乱判，是标定偏移

全部 32 条偏离，集中在两个方向相反的模式：

| expected → predicted | 条数 | 性质 |
|---|---|---|
| `bullish → strong_bullish` | 13 | 过强 |
| `bearish → strong_bearish` | 8 | 过强 |
| `bullish → neutral` | 8 | 过弱（全是权益分派「方案」类） |
| `neutral → bearish` / `→ strong_bearish` | 3 | 过弱 |

按期望档看命中结构：

```
bullish   n=23 hit=2   → strong_bullish 13, bullish 2, neutral 8
neutral   n=19 hit=16  → neutral 16, bearish 2, strong_bearish 1
bearish   n=12 hit=4   → strong_bearish 8, bearish 4
```

- `bearish` 的 4 条命中全是精确档，另 8 条一致地跳到 `strong_bearish`——**方向全对，强度升一级**。
- `neutral` 16/19，是全套最准的档。
- `bullish` 最差（2/23），但差的形态是不同的：13 条过强 + 8 条掉到 neutral。

### 那 8 条 `bullish → neutral` 需要单独说

逐条看，**8 条全部是权益分派「方案」类**（分红方案、调整每股分红金额、回购价格上限调整）。同期 6 条「实施公告」标 `neutral` 的，模型 6/6 全判 neutral。

即：**模型对"实施=事务性"的理解完全正确，只是不认同"方案=利好"**——方案本身只是宣告既定政策的分多少钱，没有超预期的增量信息。

builder 的标注规则注释里写着「权益分派只有'方案'公告才带方向信息（首次宣布提高/调整分红是回报政策信号）；'实施公告'是事务性执行通知」，而同一份注释里也记着另一条被**模型纠正过**的标注错误（"v2 评测实证：把实施公告标成 bullish 是标注错误，11 条全被模型正确判成 neutral，模型对、金标错"）。

**本次不动金标。** 为通过评测而调标注会让评测变成自我实现。把「方案」类按事务性重标后 exact hit 会从 40.7% 升到 53.7%——这个数字仅作为"金标口径可争议"的证据记录，不作为成绩。

## 四、6 条失败样本

| 类型 | 条数 | 原文摘要 |
|---|---|---|
| 拒绝打分（理由成立） | 3 | 股东会法律意见书、「仅陈述会议召集」等——**正确拒绝，不是缺陷** |
| 网关不可达（读超时） | 1 | 重试 2 次后失败 |
| 其余 | 2 | 同属超时/拒绝类 |

**拒绝打分应当算作能力而非失败**：纯表格、法律意见书被正确识别为无方向性语句并拒绝，比返回一个可疑分数有价值。评测器目前把 `refused` 计入 failures 而不计入命中分母——这个处理是对的（不拿拒绝样本摊薄或注水命中率），但报告里应把它与真失败分开计数。

## 五、两次被误归因的失败（教训）

### 5.1 「模型输出没有可解析 JSON」不是 prompt 问题，是 token 预算

报错文本长这样，极易误导：

```
LLMError: 模型输出中没有可解析的 JSON 对象：'We need answer JSON only. Need analyze...'
```

看起来像模型不听话、在输出英文思考。实际根因是 `deepseek-v4.1-flash` 的 `reasoning_content` 极长，`max_tokens` 被推理吃光后 `content` 空或只剩半截推理，`chat()` 回退取 `reasoning_content` 再解析失败。受控实验：

| max_tokens | 结果（8 条） |
|---|---|
| 16000 | 7 clean + 1 reasoning-only |
| 32000 | **8/8 clean** |

默认值原为 4000，生产 env 是 16000——**两者都偏小**。已修为默认 32000（env 可覆盖，commit `067a6e7`）。此前归档记录把这类失败归因为「网关 503」，是误判；真正的网关失败（读超时）本次只占 1 条。

### 5.2 「网关限流」也要分清是哪一种

本次 54 条串行跑完约 60-70 分钟（单条 58-73 秒）。中途曾怀疑并发导致失败，做了串行 vs 并发 3 的对照：**两种都没有出现 reasoning 泄漏**，差异只在超时数（串行 2 次、并发 3 时 4 次）与耗时（847s vs 342s）。所以并发不是推理泄漏的原因，token 预算才是。

## 六、成本事实（design 未记，本次补）

- 单条打分 58-73 秒（max_tokens=32000）；16000 时约 58s、32000 时约 73s。
- `evaluate.py` 是串行 `for` 循环，无并发 → **60 条满样本评测 = 60-70 分钟**。
- 这意味着「改一次 prompt 就跑一次评测」的迭代成本约一小时。若要提效，方向是在 evaluate 引并发（会改变执行语义与失败率，需单独评估），不是降 max_tokens。

## 七、结论与下游消费口径

**服务可用；v3 prompt 的单点质量可信**（方向 79.6%、±1 档 98.1%、正确拒绝无方向语句、正确判「实施=事务性」）。

**但五档 exact 与 confidence 加权都不可用**（40.7%、校准失败）。所以：

1. **下游只应消费「方向」（正/中/负）**，不消费五档精档、不消费 `confidence` 做加权。
2. 「拒绝打分」是一等产出：计入覆盖面，不当 neutral、不打 0 分、不重试到出结果。
3. exact 档位要达标需 prompt v4，成本是每次评测 +1 小时；**不建议为凑 exact 而调金标**。
4. **金标与评测结果必须落生产库**——这是本次暴露的最大流程缺口：不落库等于没评。

## 七之三、生产失败率高于本地的真因（2026-10-18 定位并修）

生产 43/60、本地 54/60，差的 11 条曾经让我怀疑并发。**不是并发，是 Deployment 里的一条 env**：

```yaml
- name: FD_SENTIMENT_MAX_TOKENS
  value: "16000"        # 覆盖了代码里已改成 32000 的默认值
```

`LLMConfig.from_env()` 优先读环境变量，所以镜像里 `max_tokens: int = 32000` 的默认值在生产**从未生效**。16000 正是我对照实验里「8 条中 1 条只剩 `reasoning_content`、content 空」的那一档。

已改 `fd-infra-deploy/all-services/prod/fd-sentiment.yaml` 为 `32000`（commit `4c646d8`），Pod 内实测 `env=32000 / effective=32000`。

**这条比镜像本身更值得记**：我上一轮把生产失败率归给并发，只做了「串行 vs 并发」对照就下了结论——那个对照只证明「并发不导致 reasoning 泄漏」，**没有证明「生产还有别的因素」**。真正的定位来自去读 Deployment 的 env 清单。

## 七之四、部署通道（踩过的坑，写给下一次）

`fd-prod` 命名空间由 **ArgoCD application `all-services-prod`** 管理，`syncPolicy.automated.selfHeal=true`。因此：

- `kubectl set image` / `kubectl edit` **会被自动改回**（实测 4 秒内 pod 被删、镜像回退到旧 sha）。
- 正确做法：改 `fd-infra-deploy/all-services/prod/<service>.yaml` → push → 必要时 `kubectl -n argocd annotate application all-services-prod argocd.argoproj.io/refresh=normal --overwrite` 催一次。

> **`confidence` 与正确率负相关。任何把它当可信度用的玩法都是反的——包括「只取高置信段」「按 confidence 加权」。**

**`eval_runs` 现在有 2 条真实记录**（`eval-565d5f62ecde` 旧基线与 `eval-9a0a06bd3714` 官方 run），`compare_evaluations` 可并列读出——这正是本 change 要解决的持久化缺口。

## 七之七、评测期间撞上的一次真实生产故障（密钥被轮换但 Secret 没跟）

跑 v4 评测时 60 条里有 34 条返回 `401 INVALID_API_KEY`。**第一反应差点记成"并发触发限流"**——因为我刚把 concurrency 设成 4。实际不是。

定位链：
1. `llm_calls` 表里第一个 401 在 `15:53:18`，但**最后一次成功是 `15:53:52`** —— 401 之后还有成功，说明不是密钥被整体吊销。
2. 但降速到单并发连续三次重试，仍是 401 —— 那就不是限流了。
3. 查网关 `sub2api` 库的 `api_keys` 表：Pod 里的 `sk-or-92d757...` **一条都查不到**；77 个 active 密钥里只有 1 个 `sk-or-*`，是 `sk-or-cbd76f6b...`，且它的 `last_used_at` 正是 `15:53:55`。

**结论**：网关侧做过一次密钥轮换/重建，旧 `sk-or-92d757...` 被删，但 `fd-sentiment-llm` Secret 没跟着更新。服务在旧 key 被删后还靠已建立/在途连接多撑了半分钟，所以出现"401 与成功交错"的假象——**这个现象会让人误判成限流或间歇故障**。

处置：把 Secret 的 `api-key` 换成网关里现存的 `sk-or-cbd76f6b...`，重启 Deployment，实测 `200`。回滚路径照旧（镜像不变）。

**给运维的两条**：
- 密钥轮换必须连带更新引用它的 Secret。这不是 fd-sentiment 一家的问题——`grep -r fd-sentiment-llm` 只有它在用，但同类 secret 还挂在别的服务上，轮换时容易漏。
- `sk-or-*` 这类网关 key 只有 **30 个字符**，别看到长度短就以为是截断（我一度这么以为）。长度不是校验依据，`/v1/models` 探一次就知道了。

**这条同时说明评测脚本的 failures 字段有用**：如果报告只给命中率，这次会表现为"命中率突然掉到 20%"，而 failures 里 34 条 `401` 一眼看出是凭据问题，不是模型变差。

## 七之八、prompt v4：修掉一个真实的 prompt 内部矛盾（不是调参）

### 发现过程

在核对那 4 条「没取得分数」的样本时发现：**同一个 `doc_id`、同一个 prompt 版本 v3，两次运行分别得到「拒答」和「neutral」**。起初以为是模型抖动，回读 v3 的 prompt 才发现是**内部矛盾**：

| 位置 | 原文 | 要求 |
|---|---|---|
| `system.md` 第 3 条 | 「若文本中找不到任何表达情绪/影响方向的语句（例如纯数字表格、**纯格式性文字**、无法辨识的乱码），必须拒绝打分」 | 拒答 |
| `bands.md` neutral 条 | 「董事会审议通过关于召开**年度股东大会**的议案」→ neutral | 给分 |

程序性法律意见书同时命中两条。模型在两者之间摇摆，于是同一条样本时拒时判——**这不是模型不稳定，是 prompt 没定义边界**。

### v4 的改法（digest `63e531c94d2f89bb`）

把拒答的判据从「有没有情绪词」收窄到「**读不读得出内容**」：

- **必须拒答**：编码损坏/乱码、只有数字/表格/代码等碎片、正文为空
- **不得拒答（给 neutral）**：程序性公告、按既定方案执行的分派公告、例行披露——凡能被概括出「发生了什么」的可读正文都可判

并显式写上「把可读的程序性公告判成拒答是错误：下游会把拒答读成服务没跑通，而正确结论是这条公告没有情绪信息」。v3 保持原样不动（换版不覆盖是既有约定）。

### A/B 实测（4 条定点样本，同一进程、同一模型，只换 prompt）

| doc_id | 类型 | v3 | **v4** | 金标 |
|---|---|---|---|---|
| `1225575702` | 程序性法律意见书（第四次） | neutral | neutral | neutral |
| `1225547429` | 程序性法律意见书（第三次） | **拒答** | **neutral** | neutral |
| `1225480115` | 股东会通知 | **拒答** | **neutral** | neutral |
| `13771222` | 编码损坏乱码 | 拒答 | 拒答 | bullish（金标本身有缺陷） |

**关键是这条边界是双向验证的**：v4 把可读的程序性公告从拒答改判 neutral（3 条全对），同时**没有**把乱码也放宽成 neutral（仍正确拒答）。如果只测前者，可能只是「放宽一切」；测后者才能确认是「按可读性划线」。

### 全量评测（run `eval-decaf629936d`，串行，concurrency=1）

| 指标 | v3（`eval-9a0a06bd3714`） | **v4（`eval-decaf629936d`）** |
|---|---|---|
| 取得分数 | 52 / 60 | **59 / 60** |
| exact | 46.15% | **49.15%** |
| 方向 | 82.69% | 81.36% |
| ±1 档 | 100% | 98.31% |
| 校准 | 失败 0.333 < 0.667 | **失败** 0.469 < 0.700 |

**唯一失败样本**是 `13771222`（乱码）——正确拒答，且这个金标本身就标不了（见 §7.6）。

**怎么读这组数**：
- **覆盖率是真提升**：52 → 59。v3 有 4 条拒答（3 条是误拒），v4 只剩 1 条（正确拒答）。这是这次改版的主要收益。
- **exact +3 个点在噪音范围内**：59 条样本下 3 个点约等于 2 条，方向口径反而降了 1.3 个点（48/59 vs 43/52）。不要宣称「v4 更准」。
- **校准仍失败，且形态同前**：高置信桶 46.9% < 低置信桶 70.0%。四次测量（v3 三次 + v4 一次）全部指向 `confidence` 与正确率负相关，v4 没有改变这一点——**v4 修的是拒答边界，不是置信度标定**。
- 偏离结构也几乎没变（`bullish→strong_bullish` 13 条仍是最大宗），说明强度判过头的倾向是模型/prompt 强度锚点的问题，与拒答边界无关。

### 一句话结论

**v4 该上，理由是覆盖率（52→59）和拒答正确性，不是命中率。** 命中率差异不足以下结论，校准失败依旧，`confidence` 依旧不可加权。
